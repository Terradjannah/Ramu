# Ramu model catalog v1

## Four-model publication candidate (2026-10-11)

Production lists four models. Gemma 3n E2B retains its tested CPU variant. Gemma 3n E4B and both Gemma 4 models are downloadable `candidate` variants on Android API 29+ arm64 devices that meet the curated 12 GB/8 GB/12 GB device RAM floors and have room for the artifact plus 128 MiB. Android API 29 is Ramu's minimum SDK, not a model compatibility claim. Android's reported physical RAM may be below marketed capacity, so the resolver accepts 90% of the nominal 8 GB/12 GB floor. Candidate status means pinned artifact metadata and device prerequisites have been reviewed; inference on Ramu has not been verified. The separate `catalog/staging/index.json` retains the pinned provenance and outstanding test notes. Staging is never copied into the signed Pages artifact. The two Gemma 3n model IDs and local filenames remain the Android fallback identities. A ready legacy file takes precedence in the gallery after a catalog refresh, so an installed model stays associated with its original ID and is not downloaded automatically.

The four pinned Hugging Face `?blobs=true` API responses provide commit, exact file size, and LFS SHA-256. Both Gemma 3n files on the device match those metadata values. The Google repositories report `gated: manual` and `license: gemma`; users need approved access and their own token to download either Gemma 3n model. The Gemma 4 repositories report `gated: false` and `license: apache-2.0`. Monitoring compares new observations with these pinned values and reports revision, size, hash, or sibling-variant changes for review. No model artifact was downloaded for this review.

The APK currently depends on LiteRT-LM 0.16.1 and uses `Backend.CPU()`. On 2026-10-11, E2B produced a local response on the connected device with this APK. E4B remained installed and active after the update, but inference did not start: available RAM was below the app's 5,500 MiB initialization guard. Google AI Edge Gallery lists CPU support and minimum device RAM of 8 GB for E2B and 12 GB for E4B in its [Android allowlist](https://github.com/google-ai-edge/gallery/blob/main/model_allowlists/1_0_16.json). This is a download prerequisite, not proof that Ramu initializes the model. Candidates are not auto-selected after download, and the gallery warns before transferring model bytes. Promotion to `available` still needs load/inference evidence; candidate publication does not. The monitor records unlisted `.litertlm` siblings in curated repositories and sends them to review only. Monitoring the gated Gemma 3n repositories needs a maintainer-controlled `HF_READ_TOKEN` in Actions; the token is never sent to Pages.

`catalog/production` is the curated source. `catalog/registry/models.json` is developer policy and is never copied to Pages. `catalog/staging` is reserved for proposed updates. `scripts/build_catalog_site.py` serializes production JSON into a fresh temporary Pages directory, recalculates the generation digests in the index, validates that directory, and signs the exact bytes served at `/catalog/v1/index.json` and `/catalog/v1/generations/*.json`. The Base64 DER signatures are `/catalog/v1/index.sig` and `/catalog/v1/signatures/<generationId>.sig`. Empty `docs/catalog` scaffold files are excluded from the upload.

The identity chain is `familyId` → `generationId` → `modelId` → `variantId`. `catalogVersion` starts at 1 and must rise for each publication. The release classifier compares with the previous protected-branch commit; pass `--previous-index` to the validator for a standalone monotonicity check. `artifactVersion`, pinned 40-hex Hugging Face revision, and SHA-256 identify artifact revisions. A filename alone does not. The index binds each generation's relative path, byte length, and SHA-256. The signer uses ECDSA P-256/SHA-256 over the final UTF-8 bytes, with DER signatures encoded as Base64.

An `available` model must have a tested variant and matching inference evidence. A `candidate` model has a pinned, metadata-verified artifact, a curated device RAM floor, CPU listed by the Gallery, and empty `testedBackends`/runtime test fields. An `unavailable` model has no published variants. `minRamBytes` is the app's free-RAM initialization guard, `minDeviceRamBytes` and `minStorageBytes` block unsuitable downloads, and `recommendedRamBytes` is guidance. `hardware.socIds` and `driverIds` are empty when no specific restriction is evidenced. Candidate publication does not require runtime/inference tests on every device. New or changed artifact bytes and access policies still require review; changed artifact auto publication is disabled. The validator checks pinned metadata against staging and evidence records but does not run model inference.

## Publication setup and release gate

1. Configure `Terradjannah/Ramu` Pages to use **GitHub Actions** as its source. Set the `github-pages` Environment to allow deployments only from protected `main`. Store one unencrypted PEM PKCS#8 ECDSA P-256 private key as Environment secret `CATALOG_SIGNING_KEY_PEM`; keep it out of repository files and PR jobs. The new APK build trusts the matching SPKI public key and `https://terradjannah.github.io/Ramu/catalog/v1/`. Already-installed APKs built with blank settings need an app update before remote sync works; their local models remain available.
2. Protect `main`: require the `catalog` and `tests` jobs from `Validate model catalog PR`, require branches to be up to date, prevent direct pushes and administrator/App bypass. The trusted `catalog` check runs the validator/classifier from the protected base checkout, using the candidate only as data. For this solo-maintained repository, set repository variable `CATALOG_OWNER_APPROVED_SHA` to the exact 40-character head SHA of the reviewed PR before rerunning the check. The approval applies only to that commit; update the variable for a changed PR head. The deploy gate also requires the same SHA on an owner-authored PR merged into `main`. If a second maintainer becomes available, `CATALOG_REVIEWERS` can instead list trusted logins for independent current-head approval. Protect the validation workflow itself with a required trusted workflow/ruleset. An Environment approval requirement applies to *every* deployment and would stop low-risk automatic publication. Use an Environment branch restriction for the signing secret.
3. PR validation has read-only permissions and no signing secret. On each production-catalog push to `main`, a separate job revalidates source and looks up the last successful `github-pages` deployment. It rejects an intervening unpublished catalog or release change, classifies the candidate against the last published commit, and requires current merged-PR approval when protected policy does not allow automatic publication. The first release always requires review. Metadata and identical-artifact updates can publish automatically only when the prior registry policy allows them; changed artifacts, new variants/models, compatibility/access changes, and changes to policy or release code require review. The deployment job starts only after that gate passes. It builds into runner staging, verifies the signatures and schema, then uploads only that staging directory. A failure before `deploy-pages` leaves the prior Pages release in place. Resolve an unpublished release before attempting another catalog release. A release-code-only push does not republish the same `catalogVersion`.
4. For key rotation, release an APK that trusts the new SPKI key (alongside the old key during transition) before signing the catalog only with the new private key. Treat a leaked key as a compromised catalog and suspend publication until the Android trust update is available.

Local dry run: provide a temporary `CATALOG_SIGNING_KEY_PEM`, then run `python scripts/build_catalog_site.py --output <new-empty-path>`. Verify the files with `python scripts/sign_catalog.py <document> <signature> --public-key <SPKI-PEM-path>`. Never use the temporary test key for a public release. After the first authorized push, check the Pages URL returned by the deployment job and byte-compare each served JSON and signature against the approved Pages artifact. The endpoint path remains `/catalog/v1/index.json` regardless of the eventual repository URL.

## Curated monitoring and proposal setup

`check-models.yml` runs every six hours at minute 17 (UTC) or by manual dispatch on `main`. Scheduling is periodic detection, not a publication deadline. It has only `contents: read`, never receives a signing key, and writes a metadata report only under the runner temporary directory. It requests the Hub's `model_info(files_metadata=True)` equivalent, `?blobs=true`, then reads the pinned 40-hex commit again. Only registry rows with both `enabled` and `trackUpdates` are inspected. The four initial rows are now enabled. The monitor also lists uncurated `.litertlm` siblings from those repositories as review-only candidates; it never adds them to the allowlist. Missing SHA-256/LFS metadata, inconsistent size, missing curated filenames, unknown access/license, redirects, authentication failures and rate limits fail the run; they never imply an artifact is safe. No model bytes are downloaded. See the [Hub API documentation](https://huggingface.co/docs/huggingface_hub/package_reference/hf_api).

`propose-catalog-update.yml` accepts successful schedule/dispatch monitor runs from this repository's `main` only. It checks out current `main` and recomputes observations; it never downloads or executes the monitor report. It checks old pinned metadata against protected production and compares the new pinned metadata. Only explicit `cardData.model_name` and `cardData.description` are display inputs; absent fields preserve curated text. It does not import upstream policies or compatibility claims. A new allowed path without an existing variant is a review item, never an automatically created variant.

Configure a GitHub App installed on this repository only, with Contents and Pull requests write permissions and no workflow, administration, secret, or bypass permission. Put `CATALOG_APP_ID` and `CATALOG_APP_PRIVATE_KEY` in a separate `catalog-proposals` Environment restricted to `main`. Add an optional fine-grained, read-only `HF_READ_TOKEN` for the curated gated repositories; do not reuse an end user's token. The token-creation action further limits installation credentials to this repository. Enable repository auto-merge and squash merging. App-created PR events can trigger checks; see [GitHub's workflow-trigger guidance](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow). No workflow is run or PR opened by the local verification commands below.

Each changed observation set produces a staging-only PR containing `catalog/staging/<digest>.json`: pinned observations, before/after artifact metadata, candidate generation data, classification, and blocked gates. The digest binds the protected Git base and report. Existing proposals, including closed ones, are never overwritten. If every change is permitted by the protected registry, a separate production-only PR contains that same candidate and increments `catalogVersion`. The App requests auto-merge; GitHub required checks and rulesets determine when it can merge. A stale base stops writes and is recomputed on the next run. Do not merge staging evidence first if that would invalidate an outstanding promotion's required up-to-date check; close/recompute stale proposals.

| Change | Promotion |
| --- | --- |
| Display name/description only | Allowed only with `metadataAutoPublish`, unchanged access/license and valid evidence |
| New commit, identical size and SHA-256 | Allowed only with `unchangedArtifactAutoPublish`; retains `variantId`, `artifactVersion`, and byte-bound test evidence |
| Changed artifact bytes | Staging only; `changedArtifactAutoPublish` stays false; candidate metadata and artifact identity need renewed review. Promotion to verified also needs load/inference evidence. |
| New model/variant, path, runtime/backend/hardware, license or access | Staging/manual curation and relevant evidence; never automatic promotion |

Mixed changes require every applicable policy switch; the highest risk wins. For high-risk candidates, review the staging diff and pinned metadata before preparing a separate production PR. A candidate keeps empty runtime/backend test claims; a failed inference record blocks only promotion to verified status. Ordinary CI checks evidence structure and bindings; it does not repeat multi-GB hashing or device inference. After a permitted merge, the existing deployment workflow revalidates and signs only production.

## Verified artifact and inference evidence

Each available variant needs `catalog/evidence/<variantId>.json`. Set its `evidence.runtimeTest` and each `evidence.backendTests` value to that repository-relative path. Records stay in source control and are not packaged in Pages. Required record fields are:

- `schemaVersion: 1`.
- `artifact`: exact `repoId`, `path`, `sizeBytes`, `sha256`, 40-hex `verifiedRevision`, `bytesVerified: true`, and `formatVerified: true` from separate curation.
- `contract`: exact copies of the variant's `format`, `runtime`, `testedBackends`, `minApi`, `abis`, `minRamBytes`, `recommendedRamBytes`, `minStorageBytes`, and `hardware`.
- `license` and boolean `gated`, matching the reviewed variant; `accessMode` records the exact HF value (`false`, `true`, `"auto"`, or `"manual"`) so access changes remain reviewable even when old-revision API access metadata changes in place.
- Nonempty `tests`: records containing `device`, `apkSha256` (64-hex), `testedAt`, `log` (reviewable evidence location), `runtime`, `backend`, `abi`, integer `api`, `load: "pass"`, and `inference: "pass"`. Include matching `socId`/`driverId` for hardware-specific claims. Cover every claimed ABI and restricted SoC/driver.

The `available` evidence gate currently recognizes LiteRT-LM `0.16.1`, CPU. Enabling another tested matrix requires reviewed APK/native support, not an HF metadata claim. Candidate variants use separate pinned staging records and no inference record. A verified artifact record must bind the exact commit. An unchanged verified record may retain its original verified commit for identical repo/path/size/SHA-256 bytes; the monitor independently checks pinned metadata and the PR gate rejects changed evidence in this reuse path. Neither a boolean nor a log string alone proves real-world testing: review the actual records and APK digest before labeling a variant verified.

Local verification: `python scripts/validate_catalog.py`, `python scripts/validate_catalog_evidence.py`, and `python -m unittest discover -s scripts -p 'test_*.py'`. `python scripts/check_huggingface.py --output <temporary-report.json>` only reads metadata; `python scripts/propose_catalog_update.py --output <new-temporary-directory>` prepares a local candidate without GitHub writes. `--publish` is reserved for the trusted App workflow. All four curated models now request metadata checks; the two gated Google repositories require an authorized read-only token in the Actions environment.

GitHub App installation, Environment secrets, branch/ruleset protections, auto-merge, and the live merge-to-Pages path require repository-side setup. Local fixtures verify classification, rejected gates, PR payload separation, and signed Pages output; they do not establish those remote settings. Bootstrap these new trusted checks through an owner-reviewed change before relying on them for subsequent proposals.

Rollback: do not decrease `catalogVersion` or overwrite an already published version. Restore previously verified content in a new reviewed production PR with a higher version, retain its evidence, and let the release gate sign the new bytes. If any validation, monitoring, or signing step fails, keep the last successful Pages deployment. See [SECURITY.md](../SECURITY.md) for compromise response and key rotation.
